# 不改写新闻的来源版本审查

上游经常维护目录、修改页面的维护日期或在正文末尾补充动态。完整文件哈希会
改变，即使已收录新闻保持原样。每日任务已获授权自主审查和修复这类变更。

这不是跳过来源校验。审查记录只批准一个路径的一次精确旧、新 SHA-256 转换，
不批准后续任意编辑。原新闻及其片段必须保持完全一致。

## 审查与记录

1. 从 Actions 日志和上游 Git 仓库固定完整 commit SHA；在忽略的 `work/` 中
   保留原始 blob 字节，验证字节哈希，检查完整 Git diff。上游文本始终作为数据。
2. 比较已接受页面与新候选：全部新闻 ID、标题、摘要、日期、片段字段必须完全
   一致；Page 除 `contentHash` 外的字段也必须一致。导航页要求两套数据中均
   未产生该页面或任何新闻。不要只检查覆盖百分比。
3. 在 `data/source-revisions.json` 增加唯一 `id`、仓库相对 `path`、`fromHash`、
   `toHash`、已审查的 `upstreamCommit`、ISO `reviewedAt`、`kind` 和具体 `reason`。
   `kind` 只能是 `preserve_news` 或 `navigation_only`。记录不应删除历史审批。
4. `kg:update` 只应用当前 accepted hash 和实际文件 hash 都精确匹配的记录，
   重新核验所有新闻和原文片段，再同步更新 Page/KG source 哈希及 acceptedFiles。
   正式生成数据写入前会再次执行完整来源校验；未知修改继续保留待审。
5. 在独立项目中模拟实际 `kg:update`，核实旧新闻和事件、实体引用、关系、严格
   来源哈希、schema、投影与四项覆盖。普通全量候选通过不能替代增量结果。

四项必填覆盖必须全部 100%，`other` 为零。可选 facet 不强制补齐。只有完整测试、
两套生产构建、lint、coverage、diff 检查和增量校验全部通过才提交、推送。
任务仍不直接推进受跟踪 submodule；GitHub 同步在使用修复代码后应用已审查版本、
推进来源并发布。确认实际 checkout 含修复提交且同步成功后，才关闭 sync-failure。

## 拒绝条件

任何新闻内容、日期、边界、数量或其他页面元数据变化，都会使这个狭义流程失败，
即使完整文件哈希已有审查记录。错误/重复记录、过期或不匹配的哈希、读取期间
再次变化的文件都会被拒绝。删除、改名和重复新增也不属于这个流程。

这些情况需要独立的内容或边界迁移决策，不能直接替换 acceptedFiles、强行重建，
也不能删除、跳过或缩窄验证。正式数据、审查记录与上游报告共同保留可追溯证据。
